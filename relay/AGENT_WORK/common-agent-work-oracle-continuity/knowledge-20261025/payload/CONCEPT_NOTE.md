**Interpretation, not a new Owner quote:** A handover is useful only when a cold Oracle can explain what the product/project is for, which original knowledge makes its decisions correct, what the actual source and evidence say, which assigned participants remain active, and **what it can execute NOW**. An Oracle should first solve accessible source, coordination, and test-routing gaps instead of turning every unrun check into another Owner approval. **No new work-authority or release power follows from this instruction.** Escalate a concrete unsolvable permission, input, contradictory source authority or genuine Owner-reserved acceptance decision with a tested attempted remedy.

**Problem observed:** “Knowledge checkpoint published; successor unassigned; control cutover held; next actor Owner” is a valid *limited status* but **not the entire continuity product**. It can omit source reasoning, hidden contradictions, executable next action, pending review returns, byte custody and the distinction between a blocked particular test and a blocked whole project. ## 2. The product concept: coordination that survives a chat ending

Common Agent-Work is a **repository-grounded protocol toolkit** for carrying Owner intent into small bounded engineering work, checking outputs and making the next useful move despite multiple chats and agent replacements. It is not a standalone software release or a universal tracker.

Representative user journey:

```text
Owner's exact aim + changes + engineering/custody authority
    → coordinator Oracle/OTM defines one executable task, source boundary and return
    → agent reads assigned issue/Cycle and original inputs, runs native work
    → actual issue/PR evidence + artifact relay receipt (not a fictional PASS)
    → Oracle reconciles source, candidate, negative cases and returned work
    → Oracle continues next task without unnecessary Owner loop
    → Progress Page writer projects *reconciled* public-safe change
    → successor Oracle may recover complete concept/decisions/frontier from GitHub
    → optional Owner-authorized control cutover adopts in-flight agents once
```

The key outcome is **successor execution continuity**, not an A–G document count, a quiz, an independent approval by the same author, a new GitHub folder, a local ZIP, or an automatically incremented Oracle epoch.

## 3. Vocabulary and responsibility: what a successor must NOT conflate

| Term | It means | It is not |
|---|---|---|
| **Owner outcome** | Latest explicit user-visible goal, original requirements and amendments | Oracle's preferred framework or a guessed improvement |
| **Project Oracle** | Holder of source model, decisions, task/agent reconciliation and next actor under selected mode | Automatically repository writer, independent reviewer or deployment approver |
| **OTM / standalone** | Two distinct selected coordination/publication authorities | Modes a cold worker is free to pick |
| **Native issue/PR** | Actual engineering work and evidence, candidate revision | Automatically accepted product or published Progress Page |
| **`CURRENT.json`** | Canonical assignment/control snapshot **for that activated project Cycle** | All Common projects' single central Oracle state; issue text cannot mutate it |
| **Oracle epoch** | Version of project Oracle *control* | New chat name, assignment generation or knowledge-packet revision |
| **Assignment generation** | Specific worker-task/recipient binding preserved across replacement | Permission to cancel in-flight work when Oracle changes |
| **Evidence claim** | Outcome, actor, method, exact source/candidate, limits, date and witness | PASS merely because native CI or a comment exists |
| **Artifact relay** | Public-safe bytes/receipt in Common; restricted bytes through authorized Drive | A `sandbox:` download claim that works for all chats |
| **Progress Page** | Owner-facing Home/WBS/fixtures projection of reconciled state | Separate acceptance ledger, custody storage or control authority |
| **Independent review** | Scoped contrary-case check with exposed authorship/context independence | Another chat on the same authenticated author principal |

## 6. Protected limits and why they exist

- No XML/CII product-code edits or guessed engineering semantics in this Common knowledge task.
- No new universal status schema, numerical handover threshold, multiple parallel trackers or mandatory five-task ritual.
- No process review step that delays otherwise safe Oracle-executable work; **only the affected operation** is narrowed if source/capability is truly missing.
- No fake recipient/chat/independent principal, invented Drive receipt, unobserved test, controlled-writer exclusivity, Owner trial or product PASS.
- Preserve previously returned workers, exact candidate refs and late receipts; do not replay `Cycle now` against finished assignments.
- Protected files never go in public Common; the Owner-approved root link may be passed to intended recipients, but child confidentiality, actual access and byte verification remain separate.
- Distinguish **knowledge published** from **successor prepared** from **Oracle control actually changed**; source publication does not silently authorize other roles.
