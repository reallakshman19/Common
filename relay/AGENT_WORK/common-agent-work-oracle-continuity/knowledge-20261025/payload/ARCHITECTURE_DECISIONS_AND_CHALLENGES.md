## 1. Decisions with their causal rationale

| Decision | Rejected alternative | Why it fails | Surviving wrong case / actual discriminator |
|---|---|---|---|
| **Owner aim + real original first**; distinguish latest amendments from Oracle interpretation | Start with `START_HERE` checklist and emit a framework/ZIP before source meaning | Process familiarity cannot establish technical judgment or an observable Owner outcome | Recipient passes checklist but cannot explain one difficult original-source rule; read that source and implementation, state UNKNOWN honestly |
| **Four substantive knowledge classes** — concept, architecture, decisions and frontier | A status-only A–G table of links and `PREPARED` | Cold successor knows process position but not why current design/risks exist | Show causal data/control trace, why an alternative was rejected and a decisive contrary case |
| **One executable NOW; two connected outcomes** | Exactly five compulsory actions or Owner decision at every step | Artificial dependency loops; no next work despite source/review that Oracle can actually perform | Mark a local browser NOT_RUN yet conduct accessible source checks/parallel disjoint work |
| **Selected native protocol + one project Cycle only if activated** | Let every chat choose v3.6/OTM/standalone or create a new Cycle `CURRENT` | Conflicting authoritative snapshots and role confusion | Source project has no Cycle; giving it a copied CIIFR `CURRENT` cannot authorize its agents |
| **Knowledge checkpoint is not control cutover** | Treat merged handover prompt or new chat ID as the new Oracle | No authenticated binding, readback, write isolation or late-return adoption | Both old/new sessions can write; state claim is at most PREPARED or ENFORCEMENT_UNKNOWN |
| **Preserve existing workers/returns when Oracle changes** | Reset all assignments, reassign returned G1 or discard old reviews | Duplicate work and lost evidence; a late predecessor return may overwrite current state | One assignment already RETURNED_RECONCILED with existing receipt must not be replayed by `Cycle now` |
| **Public-safe Common Option 1 first; Google Drive Option 2 next; either mandatory** | In-chat `sandbox:` ZIP, or Drive URL alone as completed delivery | Only originating session can open local file; link alone doesn't guarantee file access/bytes | Target recipient fails to download or hash the exact ZIP: `LOCAL_ONLY / NOT_TRANSFERRED` |
| **Separate producer, recipient, reviewer, Owner truth claims** | “Same digest” equals review PASS or different chat means independent | Byte identity does not prove engineering meaning; author remains author | The candidate is semantically wrong while all upload hashes match; test negative engineering case and disclose principal/exposure |
| **Progress Page is audited projection** | Manually change `data/*.json` or mark `PAGE: SYNCED` on source PR | Page diverges from native state and creates phantom authority | PR unmerged, actual site stale or no `pp_cli` execution → `PAGE: PENDING` |
| **Owner escalation only after Oracle attempts attainable solution** | Gate on reviewer appointment/Owner trial before any available source investigation | Delay without value; conflates product release with working diagnosis | Owner says continue; Oracle can inspect source/candidate and route disjoint repair now, without saying engineering was accepted |
| **No automatic numerical replacement threshold** | Replace Oracle because chat is long or elapsed minutes exceed heuristic | Context length is not demonstrated loss of concept/control | Incumbent still reconciles source/returns correctly; continue with changed-evidence refresh |

## 2. Falsifiers that matter more than checkbox completion

**F1 — Link-only successor.** A cold reader is handed `Oracle handover (read-only): .../oracle-cycles/ciifr` with no source/model context. They may locate a status JSON but cannot explain the Owner's expected user journey or why the G1/G2 split exists. **Countermeasure:** four explanatory project-specific knowledge sections, not generic advice. **Evidence:** read relevant original and code links; explain one invariant with a contradictory case, then one actual next evidence operation. **Do not claim this project-wide Common packet also proves CIIFR domain comprehension.**

**F2 — CII-specific false confidence illustrating a GENERAL source rule.** A producer counts 353 ELEMENTS and gets 13 green synthetic tests, but cannot explain field-specific version-14 pointer ownership, stored versus effective inherited values or sentinel meaning. The local ZIP is hash-verified yet Common relay publication failed. **Countermeasure:** state what original source, vendor layout and parser each actually establish; `SELF_ASSESSED`, `UNKNOWN`, `NOT_TRANSFERRED` remain distinct. **Discriminator:** a single original field with opposite-case value/ownership check; not a generic “run more tests”. This is a historical lesson, not an engineering assertion for Common.

**F3 — Stale-head review.** A reviewer checked commit A; author repairs to B. The comment is still displayed beside the PR but its PASS does not automatically apply to changed bytes. **Discriminator:** exact tested commit, changed surface and source expectation; recheck only affected claims, not all history.

**F4 — Same-account “independent” review.** A new model/chat posts from the author GitHub principal, using expected results supplied by the author. A review may be valuable as an adversarial source challenge but **authentication/independence is not established**. **Discriminator:** declared authorship, account principal, prior source/expected-value exposure and independently derived opposite-case test; don't block unrelated source inspection pending perfect independence.

**F5 — Published checkpoint, no actual knowledge.** File is committed and linked, but successor cannot identify what application works now or the next connected result. **Discriminator:** actual original concept, current source/byte candidate and meaningful future behavior in a single short read-only return. Knowledge status remains **prepared** if substantive gaps not grounded; no new scored exam.

**F6 — Fake artifact receipt.** A ZIP path exists under `/mnt/data` and its locally computed SHA matches a manifest, but recipient cannot open it. **Discriminator:** recipient separately accesses an immutable public-safe Common payload (Option 1) or authorized Drive file (Option 2) and checks actual bytes. The public receipt alone is not `BYTES_VERIFIED`.

**F7 — Silent write overlap at cutover.** State JSON says prior Oracle is retired, yet old session still has writer access or late files pending. **Discriminator:** actual permission/resource isolation and issuer/epoch command rejection with evidence; `validate.py` is not enforcement. Keep `CUTOVER_ENFORCEMENT_UNKNOWN` if unobserved.

**F8 — Returned assignment loop.** Common `CURRENT` still contains last returned builder and Owner sees “paste Cycle now”. **Discriminator:** `dispatch=RETURNED_RECONCILED`, native comment/receipt ID and selected next action; don't make a builder rerun its finished tests or reactivate generation without a new assignment.

**F9 — Cross-project Cycle confusion.** `oracle-cycles/ciifr/CURRENT.json` exists; generic Common Agent-Work is mistakenly given `project=ciifr` and a Progress `ciifr` tab. **Discriminator:** compare Owner aim/project ID/coordination mode; do not fabricate a Common-wide binding or duplicate page tab.

**F10 — Clockwork bottleneck.** Browser cannot navigate `localhost` in one chat; Oracle reports `BLOCKED` for all geometry work and asks Owner to assign reviewer, despite source, tests and disjoint work available. **Discriminator:** a two-column distinction: *specific B1 served-browser NOT_RUN* versus *source inspection and separate prototype work still doable*. Keep protected release claim pending until its actual check; don't stop everything.

**F11 — Wrong Progress Page authorship.** Agent writes source PR, Oracle says page updated, but no CLI run or published page data is witnessed. **Discriminator:** `pp_cli.py check`, actor/source audit Timeline, exact merged data SHA and actual viewer readback if claimed.

**F12 — Mandatory “five next actions” consumes available work.** Successor lists five abstract process tasks and asks Owner who to start. **Discriminator:** one explicit NOW action that a named actor can perform using already retrievable sources and an exact return location. More actions may be useful, never an extra gate.

## 3. Diagnosis tree for an unfinished handover

```text
Can incumbent reach authoritative Owner aim, native issues, source and CURRENT?
  YES → reconstruct actual concept, code/data/control architecture and decisions.
  NO  → inspect existing repo/relay/source aliases first; identify exact inaccessible record.
Has latest worker/reviewer evidence already returned?
  YES → reconcile once, preserve IDs/permalinks, check changed head only.
  NO  → execute available Oracle source challenges; route exact missing worker task.
Can requested material artifact be transferred by option 1 or option 2?
  YES → publish/read back relay and verify actual recipient custody if claiming receipt.
  NO  → local preview only; state LOCAL_ONLY / NOT_TRANSFERRED, name custodian/action.
Is the problem only one unrun test / reviewer / Owner trial?
  YES → narrow THAT engineering claim; continue all independent source/coordination work.
Is Owner truly needed for protected scope/permission/acceptance or control binding?
  YES → give one precise decision with options, attempted remedy and current evidence.
  NO  → Oracle acts directly and records one next executable return.
Has Owner selected a new Oracle and an enforceable cutover?
  NO  → prepare knowledge only; incumbent remains current.
  YES → publish authorized state CAS, adopt ongoing workers, isolate writes, read back.
```

This decision tree applies existing rules; it is **not a new workflow, compulsory five-step prerequisite, QA certification or grant of privileges**.

## 4. Evidence lattice: never promote one success to a different one

| Observed claim | Valid conclusion | Invalid promotion |
|---|---|---|
| Source docs and public payload merged on Common/main | Knowledge files exist at exact commit | Recipient read them or Oracle authority changed |
| Structural validator/CI pass | Schema relations and tested documentary contracts pass | GitHub ACLs, native solver, app/browser, Owner input PASS |
| Agent native unit and synthetic tests pass | Those exact commands/cases passed on reported/executed source | Original user file/Windows browser or independent acceptance |
| Producer-provided SHA in a receipt | Producer reported identity | Different reviewer actually downloaded / correctly interpreted semantics |
| One read-only successor source walkthrough | Source comprehension bounded to checked material | Oracle control transfer, Writer/merge/release rights |
| Authenticated, Owner-authorized CAS state publication | New declared control state current | Actual old-writer credentials revoked unless witnessed |
| Reviewer reports scoped PASS | Checked claims on exact candidate passed | All Owner criteria/other PRs/cold successor trials passed |

## 5. Distinct roles, neither role-swapping nor extra bureaucracy

- **Incumbent Oracle** keeps work moving, ensures source-backed knowledge, reconciles current evidence; may perform authorized diagnostics. If author/contributor on a relevant claim, disclose `SELF_ASSESSED`.
- **New candidate Oracle** reads and challenges source in **READ_ONLY** mode. This is not a mandatory “reconstruction report” every time an existing warm Oracle continues.
- **Review actor** adds contrary-case evidence; must separately disclose genuine account/author/expectation independence. A source challenge can proceed even when a particular non-author authorization is absent; it simply must not claim formal independent approval.
- **Owner** is needed for genuinely reserved business/engineering acceptance, changing control binding, private access grant not otherwise available, or an approved new scope—not to repeat project knowledge the Oracle can read.

## 6. Actual limits at preparation

This decision register is a **reasoned source reading**, not a live A/B experiment on cold Oracles, an actual reviewer appointment, or successful private handoff. The broader 3DC golden documents are the quality reference only. Any failure found during a real native project trial should update that project's **own** issue/Cycle receipt and the smallest relevant Common rule, not trigger an unrelated XML/CII code change.
