## Working physical model (partly proven; must challenge)

- A CII logical **node number** is an endpoint label within one model. An **ELEMENT** is a particular physical 15-row record occurrence directed `FROM -> TO`; node-pair matching may be ambiguous when pairs repeat and cannot authenticate SOURCE↔TARGET identity across independently renumbered models.
- In the verified VNext NODENAME reader, ELEMENTS header uses six fixed-width columns `[15,13,13,13,13,13]`; FROM and TO occupy `[0,15)` and `[15,28)`. The NODENAME physical pointer is in ELEMENTS record row 14 (zero-based row index 13), `[67,80)`; the pointer is 1-based when nonzero. A physical NODENAME row contains FROM and TO name fields at `[2,28)` and `[28,53)`. `0` means *no NODENAME record for that element* in this observed subset, **not** a universal sentinel rule for every auxiliary pointer.
- **Representative original source witness actually inspected by the Oracle:** original `FORNODNAME TRANSFER(1).CII`, element zero-based index **112** is `560 -> 565`, index **113** is `565 -> 570`, and *both* NODENAME pointers are **0**. This proves the missing-pointer input condition; it does not prove PR #176's structural writer is safe. Do not publish the raw original records.
- **Critical unresolved question:** process fields may be stored but not directly effective (inheritance, zero/sentinel, units, operating-case interpretation); `RIGID` record identity and pointer owner cardinality need an original-source trace. A matching-looking number or synthetic green check is not sufficient. **Do not assume** raw pressure/temperature/rigid weight bytes can be copied without their semantic and scope dependencies.
