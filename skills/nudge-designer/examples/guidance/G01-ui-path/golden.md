# Golden reference — discriminate the UI boundary

Keep overlay interception and stale detail-state attribution as hypotheses. The
supplied evidence does not choose between them. Reuse the existing diagnostic.
Prepare a browser-ready probe specification now; native execution is NOT_RUN in
this host. Do not treat missing browser access as a block to read-only test design.

| Assignment element | Filled reference |
|---|---|
| Purpose | Establish why ordinary B selection can disagree with its details while retaining keyboard behavior |
| One bounded task | A reproducible observation specification for the existing hit/state diagnostic; no repair |
| Authoritative inputs | Owner condition and supplied UI-C4/receipts; deployed identity explicitly unknown |
| Boundaries | Read-only analysis/specification; preserve keyboard; reserve any overlay/state repair pending evidence |
| Success criteria | Specify actual entrypoint/revision, viewport, CSS point, native event target/path, selected ID, header/details IDs and timing; distinguish input interception from downstream state disagreement |
| Uncertainty handling | Browser/deployment/native trace missing blocks a runtime conclusion; reuse available diagnostic and state exact execution needed |
| Evidence and continuation | Return the actual specification with supplied-versus-unrun distinctions; next browser-capable assignment executes it under real scope |

Tempting invalid continuation: remove pointer events because DOM activation passed.
That both assumes a cause and substitutes another interaction for the failing path.
Keyboard/DOM success remains useful evidence for its own boundary, not proof of
pointer success or deployed acceptance. If a later native trace reaches B but
publishes A's details, challenge the state path; do not cling to the overlay story.
