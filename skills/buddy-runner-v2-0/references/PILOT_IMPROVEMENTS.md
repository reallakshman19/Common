# v2.0 pilot improvement plan

The recovery pilot showed that a source-grounded published reconstruction can still omit material risks, leave profile evidence unknown and end before a feasible experiment. Preserve useful understanding while distinguishing what was reconstructed, qualified, attempted and accepted.

## Implemented in this revision

| Pilot finding | Change | Verification |
|---|---|---|
| Published reconstruction treated as continuation | Separate structural reconstruction and supplied continuation facts | Publication-only fixture and regression |
| Broad checkout/authentication blocker | Action, actual attempt or sourced non-attempt, observed restriction, affected scope, evidence and next feasible step | Supported/unsupported restriction regressions |
| Onboarding wait could become a false blocker | Normal Owner wait remains separate; coding claims cannot bypass it | Pending/approved/new-task fixtures |
| Unverified profile could look qualified | Explicit model/effort evidence and limits in reports; existing profile checks remain effective | Unknown-profile fixture and regression |
| Stale canonical report / omitted material risk | Source-linked disposition template and optional declared-item coverage report | Retained/omitted risk fixtures |
| Diagnosis mixed with repair acceptance | Deliverable-specific observable success in the assignment template | Human review obligation; not claimed as machine semantic validation |
| Native coding entry described generically | Require actual binding/mode/scope facts; preserve useful read-only work | Existing pinned-native tests; template review |

The new Python reports are structural and advisory. A complete blocker report does not authenticate its evidence, grant permission, certify semantic judgment or globally prohibit another authorized action. A declared-item list does not establish a complete project risk census.

## Still to establish through real use

1. Repeat the recovery pilot in an actually configured capable-model/High session; record real source, profile and capability evidence.
2. Verify that the incoming agent carries material risks, tests its highest-value claim where feasible and scopes any unresolved action accurately.
3. For a genuinely authorized coding task, establish the real native standalone binding and execute the pinned protocol with project qualifications, actual backups and outcome proof.
4. Obtain the Owner's decision on the actual reconstruction/product evidence. Independent project review remains required where that project's actual grant requires it.

No production controller, model launcher or attestation service is installed by these templates. No changes to downstream product repositories, historical handovers, older BuddyRunner packages or the pinned engineering protocol are part of this revision.
