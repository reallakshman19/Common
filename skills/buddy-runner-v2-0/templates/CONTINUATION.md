# Continuation evidence template

State the current action, its actual result and next feasible step. A reconstruction publication is its own checkpoint, never proof that the selected subsequent task ran.

## Action actually performed

```text
Activity: INVESTIGATION or CODING
Action: <actual command/tool call or concrete operation>
Source/input: <revision and authentic/derived/synthetic basis>
Oracle: <what could falsify the claim; independence limits>
Result: <observed output/exit status, not an intended result>
Evidence: <actual receipt/log/output reference>
Limits: <NOT_RUN items and what this result does not establish>
Next feasible action: <one justified continuation>
```

## Restricted continuation

```text
Attempted action: <concrete operation and whether it was actually attempted>
Observed restriction: <actual failure, tool-capability limit or directly sourced authority restriction>
Affected scope: <specific action/path/service, not a global project HOLD>
Next feasible action: <authorized alternative, further diagnosis, or the exact decision/input needed>
Evidence: <command/result or actual restriction source>
If not attempted: <why the attempt is prohibited or unavailable, with provenance>
```

Do not attempt a prohibited write, disclose private inputs, or bypass a denied permission to manufacture failure evidence. A capability inventory or directly observed Owner restriction can justify a non-attempt. Do not invent an unsuccessful checkout command.

Separate public source-read access, local runtime/browser capability, publication credentials and actual product-write permission. The absence of one does not establish absence of the others. Preserve any explicit Owner read/access restrictions. If another agent's environment differs, say so; evidence from your environment does not prove its capabilities.

Missing backups or implementation permission affect existing-file mutation. They do not by themselves prevent authorized read-only source inspection, local original-byte hashing or a non-mutating experiment. Use actual available capabilities rather than treating administrative incompleteness as a global stop.

## Normal onboarding wait

```text
Reconstruction: <submitted or explicitly approved, with source>
Task: <not supplied, or actual prompt whose authority still needs verification>
Continuation: await the required Owner decision/task; no old-task resumption
```

An approved ONBOARD session without a task is ONBOARDED_AWAITING_TASK, not a failed continuation. Do not create timers or coding work from recommendations.

## Native coding entry

Record the actual approved explicit standalone label, matching plan/task/child, criteria, current head, write scope, ownership and applicable project qualification. If an old label defaults to coordinator, identify the actual mode/binding decision needed; do not silently rewrite it. A missing coding prerequisite does not invalidate useful reconstruction or unrelated authorized investigation.

Read and execute the pinned protocol only when coding is permitted. Preserve native evidence and LOG. A prepared prompt, supplied JSON report or host invocation receipt is not evidence of completed coding/product acceptance.

The CLI accepts `--progress report.json` (or `progress` in the request, not both). Its schema is `schemas/progress.schema.json`. Results remain SUPPLIED_UNVERIFIED; the helper cannot observe or authenticate an execution from prose.
