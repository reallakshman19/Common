# Successor reconstruction template

Use concise direction first. Fill from actual source; use UNKNOWN/NOT_RUN with a reason where evidence is absent. Do not copy fixture conclusions into a project.

**Takeover / mode / continuation:** <identity; ASSISTED or RECOVERY; explicit policy>
**Original Owner outcome:** <human purpose and parent/roadmap contribution>
**Selected direction and first action:** <KEEP / IMPROVE / VERIFY_FIRST / OWNER_DECISION_REQUIRED; why>
**Source assessed:** <repository, owning issue, main/head, source and served/runtime route>
**Profile:** <configured model + effort; actual observation/provenance; limits or UNVERIFIED>

Report these separately:

| Claim | Actual status and evidence |
|---|---|
| Reconstruction | Content/source assessment; structural completeness is not semantic certification |
| Profile and implementation qualification | Actual configured profile; any applicable independent qualification still required |
| Continuation | NOT_STARTED, planned, actual reported experiment/action, or scoped restriction |
| Product outcome / acceptance | What was demonstrated and what remains unaccepted |

## Seven-part next assignment

| Part | Fill from the selected task |
|---|---|
| Purpose | Owner outcome served |
| One deliverable | One checkable diagnosis, implementation or other coherent unit |
| Authoritative inputs | Exact issue/amendments, revision, files, originals and oracle scope |
| Boundaries | Actual write grant, preserved behaviour and ownership |
| Observable success / falsifier | Evidence appropriate to this deliverable |
| Uncertainty handling | Which fact affects which action; what remains feasible |
| Evidence and continuation | Actual result/limits, unresolved items and next eligible action |

A diagnosis succeeds by identifying or falsifying a cause with measurements. A repair succeeds by improving the observed behaviour under preserved contracts. Do not promise a repaired product as the acceptance criterion for a diagnosis-only task.

## Twelve supporting sections

1. Original problem and Owner WHY.
2. Repository/source identity, migration and drift.
3. Existing implementation, contributions and ownership.
4. Original input through real output; actual consumers and first failure/unproven boundary.
5. Surviving choices, changed understanding and rejected assumptions.
6. Artifact authority and approval scope; original/derived/synthetic and oracle limits.
7. Actual execution evidence; inherited results versus freshly executed checks.
8. Gaps, findings, unknowns and material prior risks with dispositions.
9. Up to three credible ROI routes: benefit/reuse, evidence, effort/risk, dependency and falsifier.
10. Actual authority, preservation and selective rollback.
11. Remaining actions and genuine action-specific dependencies.
12. Exact next engineer start, oracle and continuation.

## Material finding / inherited item register

| ID / source | Kind | Current finding | Disposition and evidence | Affected action / next step |
|---|---|---|---|---|
| <source-linked ID> | DRIFT / DEFECT / IMPROVEMENT / INPUT_GAP / DECISION_CONFLICT | <observation versus hypothesis> | RETAIN / RESOLVED / SUPERSEDED / PARK; <reason + references> | <scope> |

Carry material source-discovered risks even when the predecessor summary omits them. Identify stale work reports and the exact newer source/evidence that supersedes them. Correct the canonical report under actual edit/backup authority, or explicitly link its supersession on an authorized reporting surface.

Discovery does not establish introduction; an introduced-defect claim needs before/after evidence. A helper-level negative does not prove an unsafe full downstream operation. Declared item IDs and dispositions aid coverage but cannot certify that every project risk was discovered or resolved.

For ONBOARD, submit the reconstruction and its limits for approval. Approval acknowledges understanding; it neither adopts every recommendation nor assigns an unspecified task.
