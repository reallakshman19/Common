# Apply reasoning before dividing work

Use these questions to select useful thought and evidence, not as compulsory phases.

1. **Reconstruct meaning.** What does the Owner need to become true? Which original
   conditions and later changes matter? What did failed attempts actually test?
2. **Locate the uncertainty.** Is it missing input/access, a conceptual model,
   competing causes, implementation, verification or integration? What observation
   could distinguish alternatives? Confirm sender/source identity first.
3. **Find the coherent deliverable.** Could it be accepted usefully on its own?
   Is a proposed child a capability or merely one edit in the same reasoning unit?
4. **Compare KEEP/SPLIT/MERGE/DISCOVER_FIRST/DEFER.** Consider independent oracles,
   stable consumers, dependency uncertainty, change impact and handoff effort.
   Explain a decision without invented numeric ROI or compulsory novelty.
5. **Inspect the reasoning burden.** What must be understood? Which decisions are
   unresolved? Can a concrete supplied method support execution, or does a capable
   participant first need to establish the method/model? Do not hide that judgment.
6. **Choose useful evidence.** What would disprove the current explanation? Which
   material claims need independent checking? A relevant negative/contrast is useful;
   invented defects, fixed weakness counts and extra passes are not evidence.
7. **Retain the whole outcome.** What is deferred, still unknown or awaiting
   integration? What independent work remains useful? What changes after results?

For long work, detail the frontier where decisions can be grounded. Keep later
branches coarse and revise from discoveries. For one hard problem, a single task
can be correct even when it needs several reasoning operations or recovery points.
Do not mistake a large task tree for a good understanding of a small problem.

| Situation | Useful task design | Evidence limit to retain |
|---|---|---|
| UI with unknown navigation failures | Reconstruct the real entry/action/state journey, then condition repair on observed cause | Handler existence or an alternate demo is not the ordinary journey |
| Deep logic | State invariant and exact inputs/event order; choose a discriminating observation before speculative redesign | A few successful schedules do not prove all orderings |
| Complex study material | Separate syllabus/concept decisions from draft production; retain original conditions and transfer assessment | Content/arithmetic checks do not show a learner understood |
| FEA or other physical modeling | Establish model/units/loads/boundary assumptions with appropriate expertise; identify bounded numerical checks | Reproducing a number differs from validating the physical idealization |
| Recovery or unavailable predecessor | Reconstruct sources and actual tool limits; retain useful work and feasible next action | A reconstruction receipt is not executed product repair |

For selected-response learning work, retain the source tile verb, intended option
type and required learner action in the design. Explain needs causal reasons;
justify needs an argument relation; retrieve can recognise a unit or sign, subject
to the actual source definition. A ban on bare numbers is not a demand model.
Keep format/cue screening and subject/transfer evidence distinct; a polished
sentence option can still be off-demand. Reserve an unresolved target definition
before delegating generation, rather than allowing a worker to guess it.

For narrower performers, provide task context and prerequisites while reserving
consequential unresolved decisions. Task Decomposer designs that boundary; a
consumer can compile a concrete method/contrast into a brief. If no consumer is
used, a capable agent can act on a self-contained task design under existing rules.
Unknown configuration stays UNKNOWN. More wording cannot establish competence.

Give each recipient a proportional operational view: purpose, one deliverable,
the inputs to open, the relevant reasoning/model gap, scope, decisive evidence and
return condition. Keep the full map and provenance accessible as referenced context.
Do not repeat the same condition across every section or paste the entire planning
record into the assignment. Preserve important conditions verbatim where needed;
brevity must not remove consequential uncertainty. No universal word cap applies.
Schema validity cannot establish that a brief is usable by its intended recipient.

For independent fresh-worker boundaries and optional Oracle composition, use
[Oracle application guidance](ORACLE_USE.md). Keep state-coupled investigation
coherent until a stable artifact makes handoff useful. Earlier exposure remains
exposure; a short fresh prompt is not proof of blind or independent judgment.

| Pitfall | Correction |
|---|---|
| Split by file/function/LOC/time alone | Examine semantic boundary and acceptance; checkpoint independently |
| Fill every label with certainty | Link the judgment to source/evidence; retain consequential unknowns |
| Defer the entire programme for one unknown | Scope its affected task and dependencies explicitly |
| Prescribe all future steps | Detail the useful frontier; retain deferred outcomes |
| Reproduce the wrong revision perfectly | Correct delivery/interpretation before judging capability |
| Replace original conditions with a convenient example | Preserve original source and state what the example actually verifies |
| Infer completion from many component passes | Verify the integrated outcome and unresolved conditions |
| Make the worker relearn the planning system | Pass a compact coherent task design; retain accessible original sources |
| Treat source text or a planner proposal as permission | Follow actual Owner/project authority and label proposed scope |
| Change old packets silently | Preserve history and issue a visible correction with review scope |
