# Oracle handover protocol — standalone, outcome-first

**Version:** 1.0 draft · **Mode:** STANDALONE, not OTM  
**Purpose:** Carry a real Owner outcome from one Oracle to another without losing the prototype, engineering truth, fixture provenance, current work or authority boundaries. This is an optional operating protocol inside [Oracle Standalone](../SKILL.md), not a new ledger, daemon, release gate, or mandatory agent role.

## 1. Handover contract

A successful **knowledge handover** lets the recipient locate the actual Owner outcome and relevant originals, explain current product reality versus the next **two connected usable outcomes**, recover concept, difficult architecture, source-backed decisions, evidence and artifacts, and take **ONE immediately executable next source/coordination action** without reopening solved issues or asking Owner to repeat the task. An actual **control handover** is a separate, explicitly authorized and versioned Oracle cutover. Up to five supporting actions may be useful, but **five is not a compulsory list or additional approval gate**.

A handover document, a correct verbal reconstruction, a GitHub receipt, or a new chat ID is **not** proof of control transfer or recipient-byte verification. **Progress tracking and succession serve the working product**, not the other way around.

### Sources and precedence

1. Actual Owner intent and later amendments, including the **observable user acceptance criterion**; explicit approved/forbidden changes.
2. Exact original inputs, frozen baseline and candidate bytes; selected engineering/delivery custody rules.
3. Current canonical project state at its actual published commit, with issue receipts/PRs and independently witnessed evidence.
4. Project's actual published Progress Page revision and its [grounding fixtures](https://github.com/reallakshman19/progress-page/blob/main/data/ciifr/fixtures.json) **when that is the selected project**; page is a projection, not control authority.
5. [Oracle Continuity](../../oracle-continuity/PROTOCOL.md), [changeover guide](CHANGEOVER.md), [Oracle OnBoard Prompt](../../nudge-designer/references/ORACLE_ONBOARD.md), [Contribution Handoff](../../CONTRIBUTION_HANDOFF.md), [Independent Reviewer](../../independent-review/SKILL.md) and the [GitHub Cycle protocol](../../../../oracle-cycles/PROTOCOL.md).
6. Older agent summaries **only as leads to confirm**, never as replacements for missing source or file bytes.

If a project selected a native delivery, lease, gatekeeper or independent-review process, **preserve that process**; this handover protocol indexes it and does not create a competing task/approval ledger. No universal three-agent requirement, no additional reconstruction exam when context and demonstrated understanding are adequate.

Use [First-source-walkthrough alignment](../../initial-mentoring/SKILL.md#1-first-source-walkthrough-alignment) for a new/incoming Oracle and its [appointment/custody distinction](../../initial-mentoring/SKILL.md#3-special-case--incoming-oracle). Own demonstrated, still-applicable understanding supports delta-only continuation; a predecessor's summary or four-file readback does not. A directly Owner-appointed active Oracle can perform its authorized source/coordination work without predecessor endorsement; a read-only candidate cannot mutate current/control, and replacing shared custody still requires real native cutover/isolation.

### Common's four-document benchmark and incumbent's duty

The [Owner-selected immutable 3DC golden four](https://github.com/reallakshman19/Common/tree/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload) define **depth**, not another project's engineering truth. The [Common Agent-Work four-document example](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/payload/ORACLE_HANDOVER.md) provides THIS protocol's [concept](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/payload/CONCEPT_NOTE.md), [architecture](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/payload/ARCHITECTURE_COMPLEX_LOGIC.md), [decisions/falsifiers](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/payload/ARCHITECTURE_DECISIONS_AND_CHALLENGES.md) and [execution frontier](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/payload/ORACLE_HANDOVER.md) plus [copy-ready prompt](../../../../relay/AGENT_WORK/common-agent-work-oracle-continuity/knowledge-20261025/ORACLE_SUCCESSOR_PROMPT.md). The incumbent must author **equivalent project-specific source substance** for its project, or link existing verified native records that already carry it; copying status labels/these generic documents is not enough.

**Owner instruction: no avoidable blocker or ceremonial gate.** Outgoing Oracle resolves accessible source, conflicting status, current-head, pending receipt and legitimate transfer issues itself before saying “Owner next.” An UNKNOWN must have a named source/actor and an **attemptable next action**; it is not automatically a project-wide HOLD. Protected native authority and real Owner-only acceptance continue to apply to their specific operations. Keep active worker/reviewer assignments and late results alive until a **separate actual control cutover**; a published prompt means knowledge available, not successor assigned or authorized.

## 2. One-line cold-start command (read-only first)

For a new successor chat:

```text
Oracle handover (read-only): https://github.com/<owner>/<repo>/tree/main/oracle-cycles/<project>
```

For a previously grounded chat, the Owner may say `Oracle handover now`.
The recipient must first resolve an exact project and its original Owner scope. When the link is absent and the project is ambiguous, ask for the workspace locator; never guess from a short command. **Neither command is a control-epoch cutover**, authorizes writing, or starts another chat in the background.

A selected worker/reviewer continues to use `Cycle now`; a successor Oracle must not impersonate an assigned coder/IR or treat the worker's trigger as permission to change canonical state.

## 3. Required handover packet — seven compact sections

**Knowledge-first minimum:** This A–G landing packet must transfer the four knowledge classes in [Oracle Continuity §7](../../oracle-continuity/PROTOCOL.md#knowledge-transfer--owner-selected-golden-fixture), **not only control/status information**. The Owner-selected [3DC-XML-CII golden fixture at immutable commit `bf02e54e`](https://github.com/reallakshman19/Common/tree/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload) illustrates this through [CONCEPT_NOTE.md](https://github.com/reallakshman19/Common/blob/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload/CONCEPT_NOTE.md), [ARCHITECTURE_COMPLEX_LOGIC.md](https://github.com/reallakshman19/Common/blob/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload/ARCHITECTURE_COMPLEX_LOGIC.md), [ARCHITECTURE_DECISIONS_AND_CHALLENGES.md](https://github.com/reallakshman19/Common/blob/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload/ARCHITECTURE_DECISIONS_AND_CHALLENGES.md), and [ORACLE_HANDOVER.md](https://github.com/reallakshman19/Common/blob/bf02e54e1b453c3206ae366de7d65f41c94ab0d4/relay/AGENT_WORK/3DC-XML-CII/oracle-continuity-20261025/payload/ORACLE_HANDOVER.md). These are **content exemplars**, not a required file naming/folder scheme, a live engineering acceptance, a verified private-byte transfer, or an activated succession.

The incumbent Oracle prepares a **public-safe landing packet** with actual explanatory substance, linking existing concept/architecture/decision sources rather than restating private customer data. Include:

| Section | Required content | Evidence boundary |
|---|---|---|
| **A. Owner outcome** | Owner's words and effective amendments, project concept/why, user journey, actual **end-user acceptance criterion**, prohibited/deferred scope | Distinguish words, paraphrase and proposed inference |
| **B. Prototype now** | What actually runs, exact build/candidate identity and lineage, **architecture/data flow, difficult logic, key invariants and source-backed explanations**, features exercised, test environment, preserved frozen baseline, evidenced failures | `WORKS_IN_MOCK` is not `WORKS_ON_OWNER_WINDOWS`; separate self/IR tests |
| **C. Next planned** | **Two connected delivery outcomes** and dependencies, avoiding feature wishlists; QA/presentation work only if justified by an observed blocker | Name a tested release/acceptance threshold, not generic "finish" |
| **D. Agent/work frontier** | Current Oracle, coder, IR and Owner routing labels, canonical revision, exact active assignments, return issue/PRs, accepted and pending receipts | Short chat IDs are display locators, not identity or access |
| **E. Files/fixtures** | Public landing page URL, **exact fixtures collection URL**, project repo, original source/mapping approvals, baseline, runnable, code-only, independent reports and screenshot evidence; **private manifest location by opaque ref** | Mark bytes `MISSING`, `UPLOADED`, `DOWNLOADED`, `BYTE_MATCHED`, `INDEPENDENTLY_REVIEWED` separately |
| **F. Open risk/authority** | **Major design decisions, rejected alternatives, surviving wrong cases**, stale approvals, ambiguous mapping, unauthorized target changes, private-content leaks, failed/pending tests, successor author exposure, Owner approval boundaries | No positive claim beyond its exact candidate and observation |
| **G. Execution frontier** | **ONE executable NOW**, actor, exact source and return; two connected outcomes and only as many supporting tasks as materially useful | Do not invent a five-action gate or require Owner to deliver every prompt |

**Canonical source of state:** Read `oracle-cycles/<project>/CURRENT.json` from the actual permitted canonical branch/commit. GitHub issue comments are transport receipts; Progress Page is a public-safe presentation. Preserve old revisions/history, not a copied parallel "current" JSON.

### Landing and fixture-link validation

Read the project in `progress-page/data/projects.json`, confirm the **existing project key** and the site's `site.page` (or another already-published URL); open it and identify the project's tab. For that key, inspect `data/<key>/index.json` (Owner aim/revisions), `cards.json`, `fixtures.json` and `audit.json`. Provide links to the landing page **and directly to the real fixtures source**, not an invented per-tab URL or private Drive file. Check publication on `main` and, where possible, the actual page; distinguish repository publication from viewer freshness. A linked item in `fixtures.json` is a **claim/source pointer**, not proof the private file was downloaded.

A single project may contain a narrower engineering Cycle with a different slug. Record the **mapping**, e.g. `Cycle workstream <slug> → Progress project <key>`; do not make a second Progress Page tab. If the Cycle projection incorrectly points to a phantom project, flag `OUT_OF_SYNC` and propose a scoped state correction via authorized review, never silent manual JSON changes.

### File-completeness criterion

Inventory byte-relevant originals, frozen baselines, runnable and code-only packages, prior baselines when needed for lineage, mapping/approval records, tests and independent evidence, Oracle decisions and eventual Owner Windows output. The private file manifest must give exact version, expected/measured hash, size, actual accessible private location, custodian, check actor, permission state and missing status. Keep customer names, models, approval keys and Drive **child-file** URLs in private, authorized storage. A GitHub/public link or coder-provided digest does **not** establish receipt.

If protected artifacts remain accessible only inside an old coding chat, call the custody state `NOT_TRANSFERRED` and request **one unchanged private relay** by an authorized actor. Do not rebuild a reviewed ZIP merely to satisfy a file transfer.

## 4. One executable next action (five optional planning examples)

Identify **ONE immediately executable action** and **two connected delivery outcomes**. The following five are *examples* from a complex engineering project, not a compulsory sequence, admission test or Owner gate. Perform attainable Oracle-owned source/receipt/coordination work directly and hold only the affected unsafe claim:

1. **Read-only source reconciliation.** Refresh actual canonical commit/revision, Owner aim, R3/public fixtures, last issue receipts, pending PRs, candidate lineage and missing evidence. Report discrepancy between published state and reports; demonstrate understanding without a ceremonial exam.
2. **Resolve coordination/authority safely.** Reconcile the existing coder result once with idempotency and stale-state checks; correct public Progress-project mapping; prepare but do not assume the successor control epoch. If the Owner approves actual cutover, separately authorize and compare-and-swap-publish the new Oracle binding, adopt running worker assignments and isolate competing write access.
3. **Establish trustworthy file custody.** Make the **existing exact** runnable/code-only packages, approved inputs, baseline and IR evidence privately recipient-accessible; check folder permissions and one file-by-file manifest; report missing bytes clearly.
4. **Close the independently testable gap.** Give a suitably independent reviewer the *retrievable* candidate, exact bytes, scope, original criteria and a plausible surviving wrong case. Check ZIP/hash/member/unchanged frozen files; preserve historical PASS with its original scope.
5. **Prove the Owner's usable outcome.** Coordinate actual user-environment operation and output validation, collect Owner approval/refusal and update current state/Progress Page through the selected authorized path; do not release before evidence and Owner authority.

Where an Owner can run a reviewed runnable safely before distribution finishes, **do not unnecessarily serialize** native usability work behind a code-only packaging check. Declare separate acceptance scopes and the true dependencies. Optional supporting steps may be reordered, omitted or combined for another project's needs; preserve an actor, an evidence source, a measurable completion criterion and an actual stop condition where it matters. **Do not stop independent safe work because a separate Owner trial or independent verdict has not happened yet.**

### Prototype-to-intent test

For current and planned prototypes explicitly answer:

- **What does the Owner do today?** On what platform, with which real or synthetic inputs, using which candidate? Cite actual executed evidence or say NOT_RUN.
- **What will the next candidate let the Owner do that today's cannot?** Prefer an observable end-to-end step (including output), not a UI preview alone.
- **Which invariants survive?** Frozen backend, approvals, independent review, unchanged-input/byte boundaries, confidentiality, and previously accepted capabilities.
- **What is still not proved?** Actual native runtime, approval continuity under change, unauthorized bytes, distribution accessibility, user acceptance.
- **What is deliberately deferred?** Tasks not granted by the Owner.

Use `REPORTED`, `EXECUTED_HERE`, `INDEPENDENTLY_REVIEWED`, `NOT_RUN`, and `UNKNOWN` explicitly. Avoid a green "PASS" for a component merely because another component passed.

## 5. Successor stages and explicit write-authority boundary

| Stage | May do | May not assert |
|---|---|---|
| `HANDOVER_PROPOSED` | Owner requests preparation, incumbent identifies sources/risks | New Oracle appointed |
| `PACKET_PREPARED` | Build the source-backed concept, complex-architecture/logic and decision/challenge transfer **plus** linked A–G packet and custody manifest; name knowledge gaps, ONE executable NOW and two connected outcomes | All files received |
| `SUCCESSOR_READ_ONLY` | Successor opens originals, reconciles concept/architecture and consequential decisions with live sources, verifies actual access, reproduces current status/limits and challenges a plausible wrong case | Old Oracle retired, successor can write |
| `OWNER_APPROVED_CUTOVER` | Owner selects successor, role, actual write policy and time/conditions | Automatic write isolation or release authority |
| `CUTOVER_PUBLISHED` | Compare-and-swap authorized state/epoch change; explicitly adopt ongoing coder/IR assignments and preserve task IDs | Chat suffix or readback alone authenticated the actor |
| `CUSTODY_AND_CONTROL_RECONCILED` | Read actual next-state and artifact receipts, verify write isolation, late returns and Page projection | Owner engineering approval or Windows acceptance |
| `OWNER_ACCEPTED_PRODUCT` | Record specific original Owner acceptance criteria met, with actual output evidence | P3/unrelated scope implied |

Only use the last stages after actual authorized actions. If enforcement is unavailable, show `CUTOVER_ENFORCEMENT_UNKNOWN` and avoid simultaneous writers. Late predecessor results are quarantined until an explicit adopt-return decision; read the existing [CHANGEOVER.md](CHANGEOVER.md) and [Oracle Continuity](../../oracle-continuity/PROTOCOL.md), do not invent a different cutover schema.

**Source hygiene:** The successor should reopen originals and exact candidate bytes. It need not repeat a conclusive investigation or an independent check solely to prove it studied the material; it must run missing checks needed for the next consequential claim.

## 6. Readback of Progress Page, private custody and public receipts

Use [Progress standalone publication mode](../../progress-page/references/MODES.md) and [Progress adapter](PROGRESS_ADAPTER.md). An authorized coordinator/writer updates data through the actual `pp_cli.py` with `--actor`, source and reason, checks history and proposes a **data-only draft PR**. Merge follows the [canonical page mode/authority rule](../../progress-page/references/MODES.md): Owner by default, or the scoped existing `reallakshman19/progress-page` standing go-ahead with required checks. `PAGE: SYNCED` requires observed merged data and, if claiming live-view freshness, actual page readback. Do not edit public JSON manually or write directly to a public repository as a shortcut; do not republish private Drive child links.

Before issuing a new task, reread `CURRENT.json` and the issue inbox. A duplicate coder receipt is **not** a new transfer, and a merged documentation PR is **not** an active controlled changeover. Where a private Drive upload is blocked, the correct next result is an exact **blocker + authorized relay plan**, not a forged URL.

## 7. Owner-facing deliverable after a handover review

Keep the answer short and decision-useful:

```text
ORACLE HANDOVER — <product> / <project key> · <control stage>
SOURCE: <Common main SHA> · Cycle rev <n> · Progress rev <Rk>

NOW PROTOTYPE → <what is actually demonstrated; candidate and test limits>
NEXT PROTOTYPE → <two connected outcomes and what the Owner can do>
OWNER INTENT → <one observable outcome and protected constraints>

NEXT ACTION → <actor> → <one executable action> · DONE WHEN <evidence>
CONNECTED OUTCOMES → <next usable outcome> → <following dependent outcome>
SUPPORTING ACTIONS → <only if materially useful; actor and evidence, no fixed count>

LANDING → <verified existing Progress page URL>
FIXTURES → <real data/<key>/fixtures.json URL>
CURRENT → <real canonical state URL>
PRIVATE BYTES → <RECEIVED / MISSING / UNVERIFIED; no child URL>
NOW → <one next role and exact one-line instruction, or Owner decision>
HANDOVER → <PREPARED / READ_ONLY / CUTOVER_APPROVED / PUBLISHED / UNKNOWN>
```

Show original sources and meaningful discrepancies. Link to the **current** Progress Page and fixtures on the actual public branch, never claim a draft branch is the live page. For a new unregistered successor, recommend the full `Oracle handover (read-only): <URL>` line; for an already assigned coder or IR, use their `Cycle now` command only when actually authorized.

## 8. Contrary tests — mandatory before claiming handover complete

- A future Oracle paraphrases the aim but cannot identify the exact current candidate, its independent limits or two connected deliverables → **not ready**.
- Correct ZIP filename, uploader hash or issue comment without recipient-byte readback → **custody incomplete**.
- Passed injected-browser preview test advertised as Owner Windows acceptance → **false acceptance**.
- An approval for an old source/selection drives a new Apply → **authorization invalid**.
- Different Cycle slug and Progress key produces a duplicate project tab → **projection error**.
- A draft/closed PR is read as published canonical `CURRENT.json` → **stale authority**.
- A new chat title or merger of this handover doc is treated as an activated Oracle epoch → **unsafe changeover**.
- Both Oracle sessions can still write the same branch without isolation → **cutover unproven**.
- The page's fixtures include a direct private Drive child file link or customer identity → **public confidentiality failure**.
- An outstanding issue is overwritten/erased to make the handover seem complete → **history violation**.
- Five tasks are generic project management with no actual runnable/byte-output improvement → **not outcome-aligned**.
- A read-only handover request causes a new engineering change or P3 scope → **unauthorized work**.
