# Oracle OnBoard Prompt

Use this optional instruction handover when a source-based working explanation
and useful next direction already exist. The available lead or Owner can prepare
it; an outgoing agent and a separately staffed Oracle are not required. It is a
prompt type, not another operating mode, admission test or review qualification.
It is a Markdown template; existing render/adapt APIs and schemas are unchanged.

## Choose the useful route

| Situation | Useful action |
|---|---|
| Established context and a next task | Issue an Oracle OnBoard Prompt using the [template](../assets/prompts/oracle-onboard.md). The receiver checks essential originals/current state and executes within existing authority. No separate reconstruction report is needed. |
| Relevant BuddyRunner, two-pass or three-pass completed | Reuse its outputs directly. An OnBoard Prompt may package the next instruction; it must not repeat the completed flow or add reconstruction. Product FAIL does not mean that the context flow is incomplete. |
| A selected context flow is still in progress | Follow its native stages. This prompt does not bypass or add stages. |
| Cold recovery with no usable context | Recover the missing meaning from original sources using the selected protocol's method. Once usable, continue; do not impose a questionnaire or a second reconstruction ceremony. |
| Same grounded task continues | Keep working. A new commit, reply or task boundary alone does not require another onboarding. |

Use this guide alone or alongside separately selected Task Decomposer, delivery
or review guidance. It neither selects those modules nor grants their authority.
Where an actual coordinator arrangement exists, preserve its dispatch/custody
division; the title Oracle does not confer permission to send or approve work.

## Prepare the instruction

Reuse the [seven-element assignment](../assets/prompts/assignment.md). Condense
history into what changes the next decision; link accessible detail. Do not make
the Owner retell the project or require a worker to infer critical context.

| Element | What travels in this prompt |
|---|---|
| Purpose | Original Owner outcome, relevant amendments and why this task matters. Retain the unfinished parent outcome as well as the local deliverable. |
| One bounded task | One checkable deliverable and a usable GUIDED method or justified OPEN investigation. State the working explanation, its evidence and a plausible alternative; mark hypotheses as hypotheses. |
| Authoritative inputs | Current candidate/artifact and original sources with direct locators, relevant revisions and byte identity where consequential. Attach completed context-flow outputs when used. Separate reported history from checks performed now. |
| Boundaries | Allowed changes/actions, behavior to preserve and reserved judgments. Retain coupled model/state decisions with someone able to justify them; do not bury them in a narrow worker's brief. |
| Success criteria | An observable result and a discriminating contrary case. Define applicable statuses/roll-up and UNKNOWN. Do not supply a target answer when independent discovery is being assessed. |
| Uncertainty handling | Actual input/tool access or UNKNOWN, the facts that could change direction, and how to handle contradiction. Missing access limits dependent proof; it does not erase valid work or stop unrelated authorized work. |
| Evidence and continuation | Native return location/binding, real observations, changed understanding, remaining parent work and the next useful action. State any standing authority for continuation; otherwise return a recommendation. |

Check the actual recipient view with the [brief check](../assets/prompts/brief-check.md).
Copy identifiers from authoritative records, not memory. If a tracker issues the
identity, preserve its native mapping and issued snapshot; do not create competing
ACK/task IDs. A source pointer must be readable through the available tools.

For a narrower worker, remove avoidable decisions while retaining WHY, relevant
state and a concrete method. A difficult measurement design still needs capable
judgment. Do not treat a short brief, model label or correct return format as proof
of competence. Adapt support from actual task-specific results.

## Receive and execute

Read the Owner/source material and actual candidate needed for the assigned task.
Check input/tool readiness early. Reuse the supplied explanation as a revisable
working model, not an authority superior to originals. Do not replay the whole
history or produce an extra understanding essay before useful execution.

If current evidence contradicts the explanation, record the exact witness and
revise the affected diagnosis or method within scope. Do not implement a repair
whose premise has just failed. Resolve discoverable facts directly; return only
consequential missing intent/authority to the appropriate participant. Continue
unaffected authorized work. Preserve the old issued view and what changed.

Execute the bounded action and check the real result against the relevant
success/contrary case. A source trace cannot establish browser behavior, a passing
test cannot establish its oracle, and a reconstruction cannot establish a repair.
Report actual commands/observations or NOT_RUN; do not promote a planned check to
evidence. Use the selected protocol's existing completion checks where applicable.

## Return evidence and direction

Keep the native reporting format. The following are contents, not a second
mandatory envelope:

- Actual task/candidate/input basis, action and decisive result, with witnesses.
- What changed in understanding: confirmed explanation, correction, drift, new
  issue or useful improvement; distinguish FACT / CLAIM / HYPOTHESIS / UNKNOWN.
- The task's completion status and the wider Owner outcome still unfinished.
- Next justified action, its actor/authority and what observation would change it.
- For a blocked action: attempt, observed restriction, affected scope and feasible
  next route. Preparation or publication alone is not execution of the action.

The available lead reconciles these with the original obligation. Retain useful
evidence; reopen only affected work. Continue an already authorized next action
when justified, without inventing a new approval loop. Do not turn a conditional
recommendation into unlimited implementation permission. A newly found unrelated
issue is recorded and prioritized, not automatically patched or made a global stop.

## Avoid the traps

| Temptation | Correction |
|---|---|
| “Oracle says the root cause is X” | Treat it as the declared explanation; verify the load-bearing premise against actual source/behavior and revise it if contradicted. |
| “The prompt is titled OnBoard, so all context is settled” | Use its actual inputs and meaning. Retrieve/check a missing material fact without an exam or full-process reset. |
| “Local task PASS means the project is done” | Preserve missing consumers, full input census, integration, real-user acceptance and release authority separately. |
| “Update the assertion until tests pass” | Justify changed expectations from original requirements. A regression exposing a real failure stays meaningful. |
| “Fresh worker means blind/independent review” | Disclose supplied conclusions and prior exposure. An instruction handover is context transfer, not proof of blind discovery or a distinct reviewer. |
| “Another prompt will fix missing access” | Report the actual restriction and feasible execution route; retain useful source work without claiming runtime PASS. |

Use [G16 raw cases](../examples/guidance/G16-oracle-onboard/raw.md) for application
and [reference distinctions](../examples/guidance/G16-oracle-onboard/golden.md)
afterward. Withhold the golden answers during fresh discovery. These are synthetic
references, not evidence of an LFEA repair or qualification of a low-thinking model.
