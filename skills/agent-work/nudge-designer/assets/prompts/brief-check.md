# Check a GUIDED brief before sending

Apply relevant checks to the finished recipient view, including handwritten briefs.
This is an authoring aid, not a gate, fixed reviewer count or extra reporting form.

1. Reconcile every action with the purpose, Owner amendments, reserved decisions,
   allowed writes and reply channel. Remove contradictions and speculative remedies.
2. Walk the method using the actual available inputs/tools. An operation cannot
   depend on a forbidden input. Supply a concrete reading/measurement procedure
   where a narrower worker would otherwise invent one.
3. Define the requested native output, relevant statuses/UNKNOWN, multipart roll-up
   and which revision counts after correction. For a tabular/count task, supply
   headers, population/exclusion rules and required reconciliation sums. For a
   channel needing an exact first line, state its matching/ID rule. Omit irrelevant
   rituals; not every task needs counts, an ACK or an attached file.
4. Resolve direct input locators/revisions and recipient access. For binary/PDF
   inputs specify a usable reader and page convention where consequential. Include
   byte size/full digest or a manifest when needed for identity; compute/check them
   from actual artifacts. Populate machine identifiers from verified data where
   tooling permits, then read back. If manual copying is unavoidable, verify it;
   do not invent unavailable hashes or imply every identifier needs a script.
5. Define ambiguous terms once, with relevant mixed/empty/missing cases. Avoid an
   open choice the recipient lacks the basis to make, without choosing an unknown
   model or verdict on their behalf.
6. Check artifact/reference provenance, prior context and permitted exposure. Keep
   target verdicts and hints out of examples used for an independent exercise.
   Use different/invented data; mark any deliberately taught target as exposed.
7. Identify who performs consequential judgment, contributor overlap and actual
   tool/configuration limits. Require SELF-ASSESSED where a producer judges itself.
8. Read the compact operational view. State material conditions once, keep WHY and
   decisive evidence, and link detailed source context. A filled template is not
   evidence the task is understood or executable.
9. For an execution request, allocate measurement design, actual sending/return
   inspection, adaptive direction and integrated verification. Check the channel
   is usable and someone owns continuation; a prepared packet is not a live loop.
   Record actual configuration/assistance instead of attributing all work to Oracle.

Before relying on a consequential PASS, challenge both its scope and test adequacy:
is the expectation grounded in the original requirement, and could a significant
plausible error within that claim still pass? Strengthen the evidence or narrow
the verdict. A filled hypothesis/alternative/test template does not answer this.
Preserve shared premise/fixture lineage and choose the receiver's role from the
actual evidence, not a fixed agent number. Oracle's own contribution is not an
independently reviewed result.

A second reader is useful for novel or consequential judgment briefs when its
expected benefit warrants it or the project requires it. After material corrections,
recheck affected interactions; earlier review does not automatically cover the fix.
Version a useful brief family and review each use's changed values, scope and
input meaning. Reuse saves authoring effort without creating trusted boilerplate.
