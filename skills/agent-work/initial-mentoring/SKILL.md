# Initial Mentoring — align understanding before consequential work

**Trigger:** A genuinely new agent, newly appointed/promoted Oracle or candidate successor begins the project's first source walkthrough. Use this within the **existing** onboarding or first work discussion, before consequential briefing or work based on the project model; do not make a separate ceremony. The responsible **Oracle** facilitates when selected; an OTM or directly coordinating Owner can do so when no Oracle is assigned. The incoming Oracle independently grounds itself rather than asking the Owner to reconstruct accessible sources.

**Point: NOT A TEST.** Three conversational themes, not a required three-question quota: the *why*, the *hard engineering model*, and the *meaningful next result*. A correct issue number, PR link, fluent buzzwords, or a templated three-part answer is not understanding. Prefer explaining or tracing **one real source example** together over interrogating a participant. Do not grade, mark PASS, demand a questionnaire, impose a fixed word count, or make mentoring an execution/admission/merge gate.

**Established participants:** Reuse only the participant's **own demonstrated, still-applicable understanding**, with a delta-only source refresh for current changes and contradictions. Reading a packet or inheriting another agent's explanation does not establish that understanding. A new commit or task boundary alone does not restart mentoring; refresh only a changed or missing premise that affects the next action.

Use with [Start Here](../START_HERE.md), [Oracle OnBoard Prompt](../nudge-designer/references/ORACLE_ONBOARD.md), [Project Home](../PROJECT_HOME_GUIDE.md) and the selected native task/custody instructions. At Oracle succession also use [Oracle Continuity](../oracle-continuity/PROTOCOL.md) and the [handover protocol](../oracle-standalone/references/ORACLE_HANDOVER_PROTOCOL.md). Those remain the authorities; this skill creates **no new control record, approval requirement, mode, test suite or mandatory artifact**.

## 1. First-source-walkthrough alignment

This is the shared alignment contract for Oracle continuity, Oracle onboarding and agent onboarding. During the first walkthrough, the recipient explains the following in **their own words with direct source pointers**, and the mentor challenges/corrects consequential differences. The incoming Oracle independently opens the significant current sources before selecting a worker's next task:

1. **Current aim and scope.** Locate the actual Owner aim and effective amendments; explain the observable end-user outcome, the immediate slice and what is deliberately deferred or forbidden. Separate Owner decisions from proposed inference, old chat stories and a broader future roadmap.
2. **One real source-to-output trace.** Follow a representative original input/record through the existing implementation or authoritative specification to an observable output; check authoritative format/domain rules where meaning depends on them. Explain the architecture rationale, critical identity/meaning changes and one rejected shortcut or plausible wrong case with a discriminating observation. Verify field-specific units, defaults/inheritance, sentinels and pointer ownership where relevant; an inventory is not effective meaning. Distinguish executed observation from expected behavior, reported tests and `NOT_RUN`.
3. **Live connected execution.** Reconcile relevant existing `PARENT → CURRENT → NEXT` WBS/task lineage with native issues, exact candidate/PR heads, accepted/pending/late returns, actor/Chat ID or `UNKNOWN`, fixture access/custody and the native return route. State whether new work continues, reuses, supersedes or parallels earlier work. Compare an existing Page's observed freshness and an activated Cycle only when selected. Name one next observable result, its actor/boundary and immediate downstream dependency. The Oracle owns the project-wide frontier and next two connected outcomes; a worker explains its bounded WBS, upstream evidence and consuming next result, without reconstructing the whole project.

If a material premise remains unverified, **name the exact source/access gap and dependent claim/action**; choose a bounded read-only source-trace or frontier reconciliation before asserting that premise or dispatching its dependent work. Safe exploration and unrelated authorized work continue. Do **not** compensate with a detailed dispatch, a guess or another Owner permission request when the source is already accessible. This conversation adds no form, mandatory artifact or approval: use the existing record only for a consequential correction. Actual missing intent, private access, writer conflict and reserved Owner decisions retain their real boundaries.

**What this prevents:** An Oracle can correctly recite the process and count a CII file's ELEMENTS, NODENAME and RIGID records, but still misunderstand stored versus effective element values, field-specific sentinel/inheritance rules, pointer ownership or downstream changes. A source census, 13 green synthetic tests and a local ZIP/benchmark do **not** resolve that distinction. The Oracle may create explicitly labelled **exploratory read-only** code/fixtures when requested, but may not call the critical engineering model verified or promise a transferable handover until one material source rule and a contrary case are traced against the actual source/specification and the recipient's permitted relay path is observed. Label partial source semantics `UNKNOWN`, local transport `NOT_TRANSFERRED`, and performance results by their exact measured workload and method. This does not prohibit independent safe source exploration.

### Shared two-way feedback — Oracle and Agent OnBoard
- Sender offers source-backed Owner outcome, framework, actual contribution/evidence and one proposed next result; this model is challengeable.
- Receiver uses a question, original-source trace, counterexample or small authorized work increment to probe both its understanding AND the sender's assumptions.
- Choose the cheapest meaningful probe; an increment is feedback, not an obligatory code quota, readiness exam or permission to edit.
- Disposition consequential feedback as **ACCEPT** (source supports premise), **CORRECT** (revise premise/task/code) or **INVESTIGATE** (bounded missing-source check).
- Sender verifies the evidence and responds; source disagreement must not be dismissed as a wrong answer or forced agreement.
- Incoming Oracle probes project architecture/WBS/outcomes; a builder probes the inherited WBS baseline, interfaces, wrong case and next consumer.
- Record only material source, disposition and changed next action in existing native records; isolate unknown claims, continue unaffected work and add no gate.
## 2. Example conversational prompts — not a questionnaire

Choose wording matched to the actual task and the recipient's experience. Ask these *as the material comes up* in the source/brief discussion, not as a mandatory form or repeated exam. The Oracle shares their working model and evidence, invites the agent to challenge it, and updates the explanation when the agent finds a contradiction.

| Alignment | Example conversational question | Look for and teach |
| --- | --- | --- |
| **Q1 — Core concept and Owner outcome** | "What real user problem are we solving, and what would make the whole result useful even if this assigned slice passes?" | User journey, original Owner aim, why the task exists, meaningful difference between partial progress and whole outcome. Contrast a superficially green but wrong result. |
| **Q2 — Difficult architecture and surviving wrong case** | "Trace one real input/value through the architecture. Where does meaning, identity or authority change? Which plausible wrong result could survive a simple test?" | Source → intermediate model → review/output, critical invariants, dependencies, alternatives, provenance and one discriminator. Use original code/spec/fixture rather than remembered claims. |
| **Q3 — Next connected engineering result** | "Given the current evidence, what should our **next observable result** be, why that first, and what does it enable or still leave unresolved?" | Meaningful action, current baseline and actor, a positive/negative observation, protected boundaries, missing evidence and next dependency. Not "work on issue ABC / PR XYZ" alone. |

**Mentoring response:** Briefly restate shared understanding, point to the relevant source, correct one material misconception if present, and return to the assigned work. If a relevant source is inaccessible, jointly state `NOT_READ` and identify the exact dependent action; do not fabricate an answer. Merge or adapt prompts when the participant's own work already demonstrates a theme; no fixed question sequence is required.

**Smallest evidence:** Use the existing assignment/return or native issue, **only if mentoring reveals a consequential correction or missing premise**. Note source, corrected understanding, what action changes, and who owns it. Ordinary conversation requires no separate mentoring ticket, ACK, checklist, ceremony, score or repeated Owner signoff. This does not substitute for independent engineering or release review.

## 3. Special case — incoming Oracle

An outgoing Oracle or authorized coordinator supplies available source-linked project knowledge, current assignments/returns and **next two connected deliverables**. Their absence does not prevent a directly Owner-appointed Oracle from recovering accessible sources itself. Apply [the shared walkthrough](#1-first-source-walkthrough-alignment) across the project rather than treating a four-file readback as continuity:

- **Concept:** Can the new Oracle explain what users are trying to accomplish, not just recite task titles?
- **Architecture:** Can the new Oracle trace one critical source-to-output relationship, a rejected shortcut and its surviving wrong case, while naming which engineering meaning is unverified?
- **Continuation:** Can the new Oracle name **which current agent owns what** and **the WBS step each agent's Progress-page block is bound to** (a block outside any WBS step, or a WBS missing from the page, is the first thing to fix), the first safe next task, the following dependent result, pending evidence and precise authority boundary? What happens if an old worker returns late?

**Preparation, appointment and custody are separate.** A candidate successor remains **read-only** and returns proposed corrections without mutating current state/control or dispatching. A direct Owner appointment permits only its actual source/coordination scope; it needs no predecessor endorsement or new mentoring approval. Replacing an incumbent on a shared control/write surface still requires the actual native cutover and old-writer isolation. A new chat, convincing explanation, golden document or `CURRENT.json` pointer does **not** revoke old writers, prove private receiver-byte access or authorize control transfer. Mark absent custody/enforcement `NOT_TRANSFERRED`/`UNKNOWN`; do not claim it.

## 4. Diagnose misalignment constructively

| Observation during discussion | Oracle's useful response |
| --- | --- |
| Correct PR/issue, but incorrect product purpose | Walk one Owner example and revise the task's WHY; do not re-run full onboarding. |
| Source and rendered/converted values are confused | Trace one field/cell/element end-to-end with provenance and applicable units/rules; distinguish source representation from effective meaning. |
| Agent assumes an unsupported sentinel, inheritance or inferred value | Locate the field-specific source rule and an opposite case. Mark unverified semantics `UNKNOWN`; do not harden a guessed conversion. |
| Report says "all converted" yet leftover source is invisible | Require a source-fragment ledger and an inspectable orphan/exception; separate coverage from correctness. |
| Oracle knows process but cannot explain domain architecture | Oracle performs targeted original-source grounding **before** giving a consequential engineering diagnosis. |
| Already assigned agent has a valid return | Reconcile the return and provide delta-only continuation; **never** ask the three questions again by default. |
| Incoming Oracle can describe the model but lacks writer/custody authority | Continue read-only source reconciliation; follow the actual cutover before any controlled writes. |

**Stop or narrow only the affected claim** when the needed original is private, the method is unverified, or a material source contradiction appears. Preserve useful completed work. For examples from the supplied Word-to-Table and CIIFR discussions (historical mentoring material, **not live test evidence**), see [worked alignment examples](examples/word-table-and-cii.md).

## 5. Oracle's one useful return

For a new agent, continue with **one already authorized meaningful task** and its existing reporting route. For an incoming Oracle, continue with **one read-only frontier reconciliation or authorized cutover step** and preservation of active assignments. A concise mentoring note, when necessary, can use:

```text
Shared project meaning: <one user outcome and source>
Critical model/contrast: <one dependency/invariant + plausible wrong case>
Next observable result: <what/why, actor, source, evidence, boundary>
Remaining UNKNOWN / HOLD: <only what affects the next action>
```

This note is optional context in the **existing** native record, not a new required document. It cannot assert `PASS`, source access, engineering acceptance, reviewer independence or Owner decisions not actually established.
