# Select understanding, method and evidence

Begin with the decision the evidence should change. Do not turn every available
check into a mandatory checklist. Keep coupled UI/state/model questions together
until one coherent result can be consumed without recreating the investigation.

| Project/task family | Necessary understanding | Useful evidence and contrary condition |
|---|---|---|
| UI/navigation | Intended user journey, actual route/state, interaction and environment | Reproduce the real path; inspect trace, hit target, visible state and errors. Compare pointer/keyboard only under declared preparations. A working component or force-click does not establish the ordinary journey. |
| Logic/data transformation | Input identity, semantics, invariants, downstream consumer | Derive examples from original rules, trace the real production path and test ambiguity/invalid input. Avoid testing a duplicate implementation with the same assumption. |
| Concurrency/long operation | Ownership of state, lifecycle, cancellation, responsiveness | Observe intermediate state and delayed/stale completion; inspect both dispatch and consumer. Final output alone can miss races or a frozen UI. |
| Learning material | Learner level, learning aim, required demand, misconceptions | Work through tasks, separate multipart demands, test transfer with suitable unexposed examples. Matching a benchmark copied into the artifact proves reproduction, not generator validity. |
| Calculation/FEA | Original givens, units, model assumptions, boundary/load cases and intended use | Recompute suitable cases, inspect model validity, equilibrium/limiting behavior and independent references where applicable. Correct arithmetic alone cannot establish the chosen physical model. |
| Research/design | Actual question, source authority, assumptions and alternatives | Trace source lineage, compare a competing explanation and name unresolved evidence. Several sources repeating one origin are not several independent confirmations. |

These are method prompts, not domain acceptance standards. Select the effective
project criteria and an appropriately capable participant for consequential model
judgment. Record what was actually assessed rather than implying professional or
project qualification from a checklist.

## Prepare a usable bounded assignment

Keep seven elements: purpose, one coherent deliverable, authoritative accessible
inputs, boundaries, observable success including a contrary case, uncertainty
handling, and evidence/continuation. If the input is a PDF, image or trace, state
how the worker can read the relevant content. Supply a tested observation method
when the worker cannot reasonably design one. Reserve consequential choices.

Before sending, read the brief as its recipient. Check contradictions between
steps, reserved decisions and publication channel; define statuses and edge cases;
make input permissions agree with step order; give exact return fields only when
they are needed. Insert consequential identifiers from actual source records.
Use invented/different data for worked examples; exposing the target answer spends
that item as evidence of unaided discovery. Do not leak an answer through a filename.

For multipart claims, preserve each part before applying a stated roll-up rule.
Keep both a known failed part and an unknown part visible. A missing test is not a
product defect; a reproducible defect is not erased by another missing test.

## Diagnose misses without a retry ritual

Distinguish input access, return-format reliability, method execution and judgment.
Inspect sender/specification/tool failures before blaming the worker. Correct a
rule using different data, then check its application where the answer was not
supplied. Change the method, boundary or participant when repeating it adds no
evidence. Reuse working brief structure while keeping every issued task sufficient
to execute without remembered conversation. No success-count threshold is defined.

For acceptance-relevant judgments, derive a few risky expectations before reading
the return when feasible. Keep them outside the worker's issued inputs, disclose
derivation timing and allow the expectation itself to be falsified. Do not impose
a private-answer exercise on routine custody checks where the expected hash is
legitimate input.

## Avoid common traps

| Temptation | Better response |
|---|---|
| All author tests pass, so accept the claim | Inspect source authority, assertion validity and the production path. |
| Another agent agreed, so it is independent | Trace authorship, exposure, method and upstream premise separately. |
| A narrower agent follows steps, so it can sign the integrated verdict | Assess the meaning of its evidence with an available capable participant; retain unestablished judgment explicitly. |
| Any missing input means stop all work | State affected claims, attempted access and next feasible action; continue unrelated checks. |
| Every review needs a weakness | Return no findings when the actual evidence supports that result. |
| More tiny tasks will solve a deep ambiguity | Resolve the premise/method with suitable judgment before delegating mechanical work. |
| A component PASS closes the parent outcome | Retain integration, original user environment and acceptance as separate claims. |
| A checksum or clean return proves truth | Verify bytes and technical support separately. |
