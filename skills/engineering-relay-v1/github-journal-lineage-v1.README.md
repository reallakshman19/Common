### Why this integration
The B2a custody API correctly returned a summary-only GitHub source receipt after real R2-B1 cold journal replay. G1's `projectPortableJournal(bytes,seed,...)` required the *actual* bundle bytes to build the R1 provenance graph. A hash-only join to arbitrary second-source inputs, or a separate repeated GitHub GET without proving identical source, would not meet the Owner's single evidence-graph intent.

**Solution: same-read composition.** An **explicitly opt-in** `readCommittedPortableJournalForLineage()` extends the staged B2a source reader to return `{custody,replay}` in private in-process memory, after a single fixed, immutable-commit GitHub GET, SHA1/SHA256 checks and real R2-B1/R2-A filesystem replay. The original `readCommittedPortableJournal()` retains **summary-only output** and returns no event bodies. The opt-in return may contain synthetic/approved PUBLIC content: never put its `replay` into logs, GitHub issue bodies, or a scoreboard without separately approved privacy and authorization.

Staged G1 `projectVerifiedPortableReplay()` calls the **same real** `assemble()`, `validate()`, `traceClaim()`, `traceEvidence()`, `traceModule()` used by G1's local and portable paths, but **does not authenticate** a caller-supplied replay on its own. New `projectCommittedGithubLineage()` binds both consumers inside the same process. It compares repository/parent, source SHA, tip, session IDs and bundle hash and generates deterministic `source_lineage_sha256` over exact source location, Git blob SHA1, bundle SHA256, manifest policy digest, tip and R1 projection digest. It does not mint Owner approval, research adoption or accepted evidence.
